# Политика повторной оценки уже пройденного контроля

**Документ:** Assessment.Reassessment.Policy
**Версия:** 1.0
**Статус:** Каноническая политика проекта
**Применяется к:** Course.Program.SVE.SelfStudy

## 1. Назначение

Этот документ определяет правила повторной оценки (`REASSESSMENT`) уже успешно пройденных LCP и CP.

Повторная оценка не должна разрушать историческую достоверность Progress и не должна автоматически отменять ранее подтверждённое успешное прохождение.

## 2. Основное правило

Если LCP или CP ранее успешно завершён:

```text
PASSED
```

то этот факт сохраняется как исторически подтверждённый.

Обычная новая попытка повторной оценки не превращает ранее успешно пройденный контроль обратно в `FAILED`, `IN_PROGRESS` или непройденный объект маршрута.

`completed.lcps` и `completed.cps` не удаляются только потому, что последующая повторная оценка дала отрицательный результат.

## 3. Reassessment

Повторная оценка уже пройденного LCP/CP является отдельным режимом:

```text
REASSESSMENT
```

Она должна быть явно распознаваема как повторная оценка ранее закрытого контроля.

Каждая повторная оценка создаётся новой попыткой Assessment с новым `assessment_id` и новым `attempt_number`. Исторические попытки не изменяются и не удаляются.

## 4. Результат Reassessment

### PASSED

Если повторная оценка завершилась успешно:

- исторический `PASSED` сохраняется;
- контроль остаётся пройденным;
- маршрут не откатывается;
- новый результат добавляется в историю попыток.

### FAILED

Если повторная оценка завершилась неуспешно:

- исторический `PASSED` сохраняется;
- контроль не считается непройденным для уже открытого маршрута только на основании этого результата;
- `completed.lcps` / `completed.cps` не удаляются автоматически;
- новая попытка может получить `REMEDIATION_REQUIRED` или `RECHECK_REQUIRED` для целей самой повторной оценки;
- Orchestrator не должен откатывать обучающегося на ранее пройденный маршрут без отдельного канонического правила.

## 5. Отличие от обычной контрольной попытки

Обычная попытка LCP/CP закрывает ещё не пройденный контроль и определяет возможность перехода дальше.

`REASSESSMENT` проверяет уже закрытый контроль и не меняет исторический факт его успешного прохождения.

Таким образом:

```text
обычный контроль:
NOT_STARTED → IN_PROGRESS → PASSED / FAILED

повторная оценка:
PASSED → REASSESSMENT → PASSED / FAILED
                         │
                         └── не отменяет исходный PASSED
```

## 6. Assessment Records

Одна попытка Reassessment хранится в том же каноническом файле LCP/CP, что и остальные попытки этого контроля.

Предыдущая попытка не переписывается.

Для Reassessment рекомендуется явно фиксировать:

```yaml
reassessment:
  required: true
  previous_successful_assessment_id: "ASM-LCP-01-01"
```

Если конкретная структура Assessment Record не содержит этих полей, связь должна быть отражена существующими каноническими полями `previous_assessment_id`, `decision` и связанными Events до отдельного расширения схемы.

## 7. Learning State

State продолжает отражать фактическое оперативное состояние маршрута.

Отрицательный результат Reassessment не должен сам по себе:

- удалять элемент из `completed.lcps` или `completed.cps`;
- возвращать текущий маршрут к ранее пройденному Lesson/Section;
- блокировать уже разрешённый следующий объект.

Если существует отдельное каноническое требование обязательной повторной оценки с последствиями для маршрута, такое правило должно быть явно определено в канонической программе и State Machine.

## 8. Events

Исторические Events не изменяются.

Каждая новая попытка Reassessment получает новые Events с собственными `event_id` и ссылкой на соответствующий `assessment_id`.

Историческое событие успешного завершения остаётся неизменным.

## 9. Валидация

При Validation Orchestrator должен различать:

1. исторически успешно закрытый контроль;
2. текущую обычную попытку контроля;
3. текущую попытку Reassessment.

Нельзя считать противоречием наличие:

```text
исторический PASSED
+
последующий REASSESSMENT FAILED
```

если Reassessment не имеет отдельного канонического последствия для маршрута.

## 10. Ограничение

Нельзя использовать Reassessment как способ обхода обязательной коррекции обычного непройденного контроля.

Если контроль ещё не был успешно пройден, применяется обычная State Machine:

```text
FAILED → REMEDIATION → RECHECK
```

`REASSESSMENT` применяется только к контролю, который уже имел подтверждённый успешный результат.
