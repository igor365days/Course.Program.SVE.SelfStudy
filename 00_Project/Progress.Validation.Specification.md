# Спецификация проверки согласованности Progress

**Документ:** Progress.Validation.Specification
**Версия:** 1.0
**Статус:** Каноническая спецификация проекта
**Применяется к:** Course.Program.SVE.SelfStudy

## 1. Назначение

Определяет проверки, которые должны выполняться перед продвижением обучающегося и при восстановлении Progress.

Основные источники:

- `01_Course/Course.Program.SVE.SelfStudy.md`
- `00_Project/Learning.State.Machine.md`
- `00_Project/Learning.Progress.Protocol.md`
- `00_Project/Learning.State.File.Standard.md`
- `00_Project/Learning.Events.File.Standard.md`
- `00_Project/Assessment.Record.File.Standard.md`
- `00_Project/Assessment.Verification.Policy.md`

## 2. Проверка маршрута

Проверить:

1. текущие `section_id`, `lesson_id`, `unit_id` существуют в каноническом курсе;
2. Unit принадлежит указанному Lesson и Section;
3. LCP принадлежит указанному Lesson;
4. CP принадлежит указанному Section;
5. следующий объект соответствует каноническому порядку;
6. количество объектов соответствует канонической программе: 18 Lessons, 56 Unit, 18 LCP, 5 CP.

## 3. Проверка State

Проверить:

- `progress_status` имеет допустимое значение;
- `current.phase` согласована с `control_type`;
- `current.status` допустим для текущего объекта;
- `next_action` существует в State Machine;
- `next_action` достижим из текущего состояния;
- `blocking.active` не противоречит `next_action`;
- `remediation.active` ведёт к `REMEDIATION` или `RECHECK`;
- `completed` содержит только подтверждённые объекты;
- `last_event_id` существует, если указан;
- `last_assessment_id` существует, если указан.

## 4. Проверка Events

Проверить:

- каждая строка является валидным JSON;
- `event_id` уникален;
- события расположены хронологически;
- `type`, `result`, `verification` и `actor` имеют допустимые значения;
- применимые идентификаторы существуют в каноническом маршруте;
- `assessment_id` существует при его использовании;
- исторические события не переписаны для имитации нового результата.

## 5. Проверка Assessment Records

Для каждой завершённой попытки проверить:

- `assessment_id` уникален;
- `attempt_number` последователен;
- `control_id` соответствует файлу;
- `type` соответствует LCP или CP;
- обязательные компоненты присутствуют;
- каждый обязательный компонент имеет `execution`, `verification`, `result`;
- `NOT_VERIFIED` не используется как положительное подтверждение;
- `PASSED` всей попытки возможен только при положительном результате всех обязательных компонентов;
- повторная попытка не удаляет предыдущую;
- `previous_assessment_id` указывает на непосредственно предшествующую попытку, если это recheck.

## 6. Межфайловые связи

Проверять цепочки:

```text
Learning Event.assessment_id
        ↕
Assessment Record.assessment_id
        ↓
Learning.State.last_assessment_id
```

и:

```text
Learning Event.event_id
        ↓
Learning.State.last_event_id
```

Ссылки не должны указывать на несуществующие записи.

## 7. Проверка Verification

Для каждого обязательного компонента:

```text
execution = COMPLETED
verification = AI_VERIFIED или USER_CONFIRMED
result = PASSED или ACCEPTED
```

допускается только если это соответствует Verification Policy и каноническому определению контрольной точки.

`NOT_VERIFIED` обязательного компонента блокирует успешное завершение.

## 8. Проверка перехода

Перед выдачей следующего действия Orchestrator обязан проверить:

```text
CHAT ROLE
→ актуальный State
→ канонический объект
→ prerequisites
→ blocking
→ remediation
→ recheck
→ обязательные результаты
→ State Machine
→ next_action
```

Если хотя бы один обязательный элемент не подтверждён, продвижение блокируется.

## 9. Критические несоответствия

Следующие состояния считаются критическими:

- State указывает на несуществующий объект;
- `next_action` нарушает маршрут;
- завершённый объект не подтверждён Events/Assessments;
- Assessment имеет `PASSED` при непройденном обязательном компоненте;
- `NOT_VERIFIED` трактуется как положительное подтверждение;
- `last_event_id` или `last_assessment_id` отсутствует в источнике;
- история попыток противоречит State;
- активный blocking обойдён;
- Progress смешивает тестовые и реальные данные.

При критическом несоответствии продвижение запрещено до восстановления согласованности.

## 10. Восстановление

Порядок:

1. остановить продвижение;
2. перечитать State;
3. перечитать Events;
4. перечитать связанные Assessments;
5. определить последнее подтверждённое состояние;
6. сопоставить его с каноническим маршрутом;
7. восстановить State;
8. повторно выполнить все проверки;
9. только после успешной проверки определить `next_action`.

## 11. Инварианты

1. Канонический курс не изменяется ради Progress.
2. Progress не изменяет канонический маршрут.
3. История не теряется.
4. `State` является снимком, а не независимой историей.
5. `Events` являются историческим журналом.
6. `Assessments` являются источником подробных результатов контроля.
7. `next_action` не может обходить обязательный этап.
8. Все чаты используют один Progress.
9. Тестовые данные не смешиваются с реальными.
