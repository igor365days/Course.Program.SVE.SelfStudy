# Спецификация Course Orchestrator

**Проект:** Course.Program.SVE.SelfStudy  
**Спецификация:** v2.2  
**Статус:** Архитектура до запуска

## 1. Назначение

Course Orchestrator — логический управляющий слой учебной системы. Он управляет маршрутом обучающегося по каноническому курсу, проверяет переходы, управляет последовательностью Unit, LCP и CP, фиксирует значимые события, поддерживает текущее состояние и определяет следующее разрешённое действие.

Цель — устойчивый результат обучения, а не максимальная скорость прохождения.

## 2. Архитектурное положение

```text
Канонический курс
      │
      ├── Course / Unit / Lesson / LCP / CP
      ├── правила маршрута
      └── Verification Policy
              │
              ▼
      COURSE ORCHESTRATOR
              │
      ┌───────┼────────┐
      ▼       ▼        ▼
Learning   Assessment  State
Events     Records     Snapshot
      └───────┼────────┘
              ▼
           GitHub
        04_Progress/
```

Orchestrator — логическая роль. Не предполагается наличие у ChatGPT Project программируемого API конечного автомата.

## 3. Роли чатов

Project Instructions применяются ко всем чатам Project. Поэтому общая политика оркестрации используется во всех чатах, а конкретный режим задаётся явным маркером роли.

Внутренний `chat_id` ChatGPT не считается доступным модели и не используется для выбора роли.

Каждый рабочий чат должен начинаться с одного из маркеров:

```text
CHAT ROLE = ORCHESTRATOR
PROJECT = Course.Program.SVE.SelfStudy
```

или

```text
CHAT ROLE = LEARNING
PROJECT = Course.Program.SVE.SelfStudy
```

### ORCHESTRATOR

Отвечает за:

- чтение и проверку Progress;
- определение текущей позиции маршрута;
- определение следующего разрешённого действия;
- координацию продвижения и контрольных точек;
- запись и поддержание Progress;
- краткие отчёты;
- блокировку неразрешённых переходов.

Orchestrator не заменяет полноценную Learning Session.

### LEARNING

Отвечает за:

- непосредственное обучение;
- объяснение канонического материала;
- практику и упражнения;
- проверку Unit, когда это предусмотрено маршрутом;
- выполнение LCP/CP, когда это предусмотрено;
- получение требуемых доказательств.

LEARNING обязан соблюдать канонический маршрут и Progress и не может самостоятельно пропускать обязательные этапы.

### Общее состояние между чатами

ORCHESTRATOR и LEARNING используют GitHub `04_Progress/` как общее внешнее постоянное состояние. История конкретного чата не является постоянной базой Progress.

```text
LEARNING CHAT
     │
     │ WRITE Progress
     ▼
   GitHub
     │
     │ READ Progress
     ▼
ORCHESTRATOR CHAT
```

Это правило было проверено экспериментально: LEARNING записал тестовое событие в GitHub, после чего ORCHESTRATOR непосредственно прочитал тот же файл и определил следующее разрешённое действие.

Project Sources не следует использовать как изменяемую оперативную базу Progress. Они служат источником контекста, материалов и спецификаций. Актуальное оперативное состояние при необходимости читается непосредственно из GitHub.

Если роль отсутствует или неоднозначна, её нельзя угадывать — необходимо запросить её у пользователя.

## 4. Канонический маршрут

Курс содержит **18 исходных уроков, 56 Unit, 18 LCP и 5 разделов с 5 CP**.

```text
Lesson 1: Unit → ... → LCP-01
Lesson 2: Unit → ... → LCP-02
...
Lesson 18: Unit → ... → LCP-18

После последнего урока раздела:
LCP → CP → следующий раздел
```

Каждый Unit относится к одному исходному уроку и одному разделу. Unit внутри урока идут последовательно.

## 5. Иерархия контроля

```text
UNIT VERIFICATION
       ↓
LCP — контроль на уровне урока
       ↓
CP — контроль на уровне раздела
       ↓
NEXT SECTION
```

## 6. Проверка

Правила определяются в `Assessment.Verification.Policy.md`.

Допустимые источники:

- `AI_VERIFIED` — AI оценил доступные доказательства;
- `USER_CONFIRMED` — пользователь подтвердил выполнение действия, которое AI не может надёжно проверить;
- `NOT_VERIFIED` — требуемые доказательства отсутствуют.

Обязательный компонент со значением `NOT_VERIFIED` блокирует завершение контроля. `USER_CONFIRMED` нельзя выдавать за AI-проверку.

## 7. Основные обязанности Orchestrator

Orchestrator:

- читает состояние обучающегося;
- читает канонический маршрут и определения;
- проверяет предварительные условия;
- определяет следующее действие;
- координирует Learning Session;
- проверяет завершение Unit;
- фиксирует значимые события;
- обновляет состояние после значимых переходов;
- запускает LCP после последнего Unit урока;
- оценивает LCP и организует целевую коррекцию/повторную проверку;
- запускает CP после LCP всех уроков раздела;
- блокирует следующий раздел до выполнения требований CP;
- запрашивает USER_CONFIRMED, когда это требуется;
- создаёт/обновляет Assessment Record;
- формирует краткие отчёты;
- не изменяет канонический курс ради фиксации Progress.

## 8. Иерархия источников истины

```text
КАНОНИЧЕСКИЙ КУРС
Что должно изучаться и контролироваться.

ASSESSMENT RECORDS + LEARNING EVENTS
Что фактически произошло и какие результаты получены.

LEARNING STATE
Текущий оперативный снимок.
```

`Learning.State.yaml` — не самостоятельная историческая истина; он может быть восстановлен из событий и записей оценивания.

## 9. Хранение Progress

```text
04_Progress/
├── Learning.State.yaml
├── Learning.Events.jsonl
└── Assessments/
    ├── LCP-01.yaml ... LCP-18.yaml
    └── CP-01.yaml ... CP-05.yaml
```

Стандарты определяются в:

- `Learning.State.File.Standard.md`
- `Learning.Events.File.Standard.md`
- `Assessment.Record.File.Standard.md`

## 10. Начало сессии

1. Определить роль, если она нужна.
2. Прочитать `Learning.State.yaml`, если Progress инициализирован.
3. Прочитать соответствующий канонический маршрут и текущие определения.
4. Проверить согласованность состояния с маршрутом.
5. При отсутствии/противоречии состояния восстановить его по Events и Assessment Records.
6. Определить следующее разрешённое действие.
7. Начать или продолжить соответствующую Learning Session.

Обучающийся не должен вручную восстанавливать маршрут.

## 11. Протокол Unit

### START_UNIT

1. Проверить, что Unit является следующим элементом маршрута.
2. Прочитать каноническое определение.
3. Записать `UNIT_STARTED`.
4. Установить `IN_PROGRESS`.

### CONTINUE_UNIT

Проводить Unit по каноническому определению и текущему состоянию. Не создавать событие для каждого сообщения.

### VERIFY_UNIT

1. Определить обязательные компоненты.
2. Применить Verification Policy.
3. Выполнить AI-проверку там, где она разрешена.
4. Запросить подтверждение пользователя там, где оно требуется.
5. Определить недостатки.
6. При выполнении требований записать `UNIT_VERIFIED` и завершить Unit.
7. При недостатках оставить Unit открытым для коррекции.

### COMPLETE_UNIT

Unit завершён только при наличии приемлемых доказательств всех обязательных требований. Затем определить следующий Unit или LCP.

## 12. Протокол LCP

LCP доступен после выполнения требований всех Unit исходного урока.

### START_LCP

1. Проверить Unit-предпосылки.
2. Прочитать каноническое определение LCP.
3. Записать `LCP_STARTED`.
4. Сделать LCP текущим контролем.

### COMPLETE_LCP

1. Выполнить обязательные компоненты.
2. Применить Verification Policy.
3. Записать Assessment Record.
4. Записать соответствующее Learning Event.
5. При успехе открыть следующий урок.
6. При неуспехе определить недостатки и начать коррекцию.

### LCP_REMEDIATION

Коррекция должна быть целевой и связанной с выявленными пробелами, а не автоматическим повторением всего урока.

### LCP_RECHECK

Повторная проверка создаёт новую Assessment Record, связанную с предыдущей. Предыдущий результат сохраняется.

## 13. Протокол CP

CP доступна после прохождения LCP всех уроков раздела.

### START_CP

1. Проверить предпосылки раздела.
2. Прочитать каноническое определение CP.
3. Записать `CP_STARTED`.
4. Сделать CP текущим контролем.

### COMPLETE_CP

1. Выполнить обязательные компоненты.
2. Применить Verification Policy.
3. Создать/обновить Assessment Record.
4. Записать Learning Event.
5. При успехе открыть следующий раздел.
6. При неуспехе начать целевую коррекцию и повторную проверку.

## 14. Протокол событий

Записывать только значимые события, влияющие на состояние.

```text
UNIT_STARTED
UNIT_VERIFIED
REVIEW_REQUIRED
USER_CONFIRMATION_REQUESTED
USER_CONFIRMED
LCP_STARTED
LCP_COMPLETED
REMEDIATION_STARTED
REMEDIATION_COMPLETED
RECHECK_REQUIRED
CP_STARTED
CP_COMPLETED
```

Обычный диалог, объяснение, вопрос или отдельное упражнение автоматически не являются Learning Event.

Исторические события добавляются и не переписываются молча.

## 15. Протокол Assessment Record

Для каждой попытки LCP/CP сохранять:

- идентификатор;
- дату/время;
- статус/результат;
- обязательные компоненты;
- статус выполнения;
- источник проверки;
- сильные стороны;
- недостатки;
- коррекцию;
- связь с повторной проверкой;
- решение о продвижении.

Подробности оценивания хранятся в Assessment Records, а не в потоке событий.

## 16. Обновление Learning State

После значимых переходов обновлять `Learning.State.yaml`, в частности после:

- начала/завершения Unit;
- начала/завершения LCP;
- начала/завершения CP;
- входа/выхода из коррекции;
- завершения повторной проверки;
- открытия нового урока или раздела.

Состояние должно отражать последние подтверждённые исторические данные.

## 17. Протокол записи в GitHub

При изменении существующего Progress-файла:

1. Прочитать файл.
2. Получить текущий blob SHA.
3. Выполнить минимальное изменение.
4. Записать полное новое содержимое с текущим SHA.
5. Снова прочитать файл.
6. Проверить результат и структуру.

Не выполнять параллельные записи в один файл.

При устаревшем SHA сначала перечитать файл. Нельзя вслепую перезаписывать более новую версию.

Перед созданием нового файла убедиться, что путь не существует.

## 18. Принцип атомарности

Значимый переход должен сохранять внутреннюю согласованность Progress:

```text
ASSESSMENT RESULT
      ↓
LEARNING EVENT
      ↓
LEARNING STATE
```

Если промежуточная запись не удалась, нельзя заявлять об успешном сохранении всего перехода до проверки состояния репозитория.

## 19. Выбор следующего действия

Перед разрешением следующего действия проверить:

1. текущий канонический элемент;
2. предпосылки;
3. проверку Unit;
4. доступность LCP;
5. доступность CP;
6. доказательства обязательных компонентов;
7. отсутствие блокирующих недостатков;
8. соответствие Progress каноническому маршруту.

Допустимые действия:

```text
START_UNIT
CONTINUE_UNIT
VERIFY_UNIT
REQUEST_USER_CONFIRMATION
START_LCP
LCP_REMEDIATION
LCP_RECHECK
START_CP
CP_REMEDIATION
CP_RECHECK
OPEN_NEXT_LESSON
OPEN_NEXT_SECTION
```

## 20. Отчётность

Отчёты формируются по запросу из структурированного Progress и не дублируются постоянно.

Краткий отчёт содержит:

- Section / Lesson / Unit;
- прогресс Unit;
- прогресс LCP;
- прогресс CP;
- последний значимый результат;
- блокирующую проблему или коррекцию;
- следующее разрешённое действие.

## 21. Архитектура Learning Session

Unit — учебный объект, а не обязательный отдельный чат.

По умолчанию используется непрерывная Learning Session для последовательных Unit и, где удобно, LCP. Новый чат допустим при чрезмерном размере или потере полезного контекста.

Обучающийся не должен создавать отдельный чат для каждого Unit.

Orchestrator — управляющий слой, а Learning Session — слой непосредственного обучения.

## 22. Ошибки и восстановление

Если Progress отсутствует, повреждён или противоречив:

1. Не придумывать прогресс.
2. Прочитать исторические Events и Assessment Records.
3. Сопоставить их с каноническим курсом.
4. Восстановить наиболее безопасное согласованное состояние.
5. При неоднозначности остановить продвижение и запросить минимальное уточнение.
6. При необходимости записать подтверждённое исправление как значимое событие.

## 23. Что запрещено

Orchestrator не должен:

- считать историю чата постоянной базой Progress;
- требовать отдельный чат для каждого Unit;
- представлять подтверждение пользователя как AI-проверку;
- молча удалять исторические результаты;
- изменять канонический курс ради Progress;
- заявлять о сохранении без проверки записи в GitHub;
- создавать подробные постоянные отчёты без необходимости.

## 24. Принципы проектирования

1. Канонический курс и Progress обучающегося — разные сущности.
2. Unit, LCP и CP — разные уровни контроля.
3. Unit и чат — разные понятия.
4. Завершение требует приемлемых доказательств.
5. Источник доказательства должен быть явным.
6. USER_CONFIRMED применяется только там, где это разрешено.
7. LCP управляет переходом между уроками.
8. CP управляет переходом между разделами.
9. Неудача контроля вызывает целевую коррекцию.
10. История Progress ведётся добавлением новых записей.
11. Learning State — оперативный снимок.
12. GitHub — внешний слой постоянного хранения Progress.
13. Обучающийся не должен вручную восстанавливать маршрут.
14. Протокол должен быть совместим с будущим программным Orchestrator.
15. Роль чата задаётся явно, а не по недоступному `chat_id`.
16. Project Instructions задают общие правила, а роль чата определяет рабочее поведение.
17. Постоянное состояние между чатами передаётся через GitHub `04_Progress/`, а не через историю чатов.
