# Протокол Progress — Course.Program.SVE.SelfStudy

**Документ:** Learning.Progress.Protocol
**Версия:** 1.1
**Статус:** Канонический протокол проекта
**Применяется к:** Course.Program.SVE.SelfStudy

## 1. Назначение

Этот документ формализует полный цикл фиксации фактического прохождения курса: от начала Unit до перехода к следующему Unit, LCP или CP.

Progress — внешнее постоянное состояние конкретного обучающегося. Он хранится в GitHub и является общим для рабочих чатах Project.

История чата не является постоянным Progress.

## 2. Состав Progress

```text
04_Progress/
├── Learning.State.yaml
├── Learning.Events.jsonl
└── Assessments/
    ├── LCP-01.yaml ... LCP-18.yaml
    └── CP-01.yaml ... CP-05.yaml
```

Точные форматы определяются:

- `Learning.State.File.Standard.md` — State;
- `Learning.Events.File.Standard.md` — Events;
- `Assessment.Record.File.Standard.md` — Assessment Records.

## 3. Иерархия данных

```text
Канонический курс
      │
      │ маршрут и требования
      ▼
учебная работа / контроль
      │
      ▼
Learning Event + Assessment Record
      │
      ▼
Learning State
      │
      ▼
следующее разрешённое действие
```

Канонический курс определяет, что должно происходить. Events и Assessments фиксируют, что фактически произошло. State показывает текущее оперативное состояние.

## 4. Роли

### ORCHESTRATOR

Читает Progress, проверяет маршрут и prerequisites, определяет следующее разрешённое действие, координирует Learning Session, контролирует переходы и поддерживает Progress.

### LEARNING

Проводит обучение, практику, предусмотренные проверки и получение требуемых доказательств.

Обе роли используют один GitHub Progress.

## 5. Начало сессии

1. Определить роль.
2. Прочитать актуальный `Learning.State.yaml`, если он существует.
3. Прочитать соответствующее каноническое определение курса.
4. Проверить prerequisites и согласованность State с Events/Assessments.
5. При противоречии восстановить State из исторических данных.
6. Определить следующее разрешённое действие.
7. Только затем продолжать обучение или управление маршрутом.

Если состояние неоднозначно, продвижение блокируется.

## 6. Unit

### START_UNIT

Unit должна быть следующим разрешённым элементом. Записываются `UNIT_STARTED` и соответствующее состояние `IN_PROGRESS`.

### CONTINUE_UNIT

Проводится каноническая учебная работа. Обычные сообщения не становятся Events автоматически.

### VERIFY_UNIT

1. Определить обязательные компоненты.
2. Применить Verification Policy.
3. Выполнить AI-проверку там, где она разрешена.
4. Запросить пользовательское подтверждение там, где оно предусмотрено.
5. Зафиксировать результат компонентов.
6. Определить итог Unit.

### PASSED

Приемлемые результаты всех обязательных компонентов → `UNIT_VERIFIED` → обновление State → следующий Unit или LCP.

### НЕУСПЕХ / NOT_VERIFIED

Следующий обязательный элемент не открывается. Фиксируется `REVIEW_REQUIRED`, организуется целевая коррекция и затем повторная проверка.

## 7. LCP

LCP доступна только после завершения всех Unit соответствующего урока.

### START_LCP

Проверить prerequisites, прочитать каноническое определение, записать `LCP_STARTED` и сделать LCP текущим контролем.

### COMPLETE_LCP

1. Выполнить обязательные компоненты.
2. Применить Verification Policy.
3. Создать или обновить Assessment Record соответствующего `LCP-XX.yaml`.
4. Новую попытку записать как новый элемент `attempts` с новым `assessment_id`.
5. Записать связанное Learning Event.
6. Определить `PASSED` или `FAILED`.

При успехе открыть следующий урок. При неуспехе: `FAILED → REMEDIATION → RECHECK → решение о продвижении`.

## 8. CP

CP доступна только после прохождения всех LCP раздела.

### START_CP

Проверить prerequisites, прочитать каноническое определение, записать `CP_STARTED` и сделать CP текущим контролем.

### COMPLETE_CP

1. Выполнить обязательные компоненты.
2. Применить Verification Policy.
3. Создать или обновить Assessment Record соответствующего `CP-XX.yaml`.
4. Новую попытку записать как новый элемент `attempts`.
5. Записать связанное Learning Event.
6. Определить результат и решение о продвижении.

При успехе открыть следующий раздел. При неуспехе — целевая коррекция и повторная проверка.

## 9. Проверка компонентов

Для каждого обязательного компонента отдельно фиксируются:

- `execution`;
- `verification`;
- `result`;
- `deficiency_ids`, если применимо.

`verification` принимает только:

```text
AI_VERIFIED
USER_CONFIRMED
NOT_VERIFIED
```

`USER_CONFIRMED` — подтверждение выполнения пользователем; это не AI-проверка.

Обязательный компонент с `NOT_VERIFIED` не может считаться завершённым.

## 10. Learning Events

Канонические типы:

```text
UNIT_STARTED
UNIT_VERIFIED
REVIEW_REQUIRED
USER_CONFIRMATION_REQUESTED
USER_CONFIRMED
LCP_STARTED
LCP_COMPLETED
REMEDIATION_STARTED
REMEDIATION_COMPLETED
RECHECK_REQUIRED
CP_STARTED
CP_COMPLETED
```

Каждое событие содержит уникальный `event_id`, `timestamp`, `type`, `actor` и применимый контекст. События добавляются в конец `Learning.Events.jsonl`.

## 11. Assessment Records

Один файл соответствует одной канонической контрольной точке:

```text
LCP-01.yaml
...
LCP-18.yaml
CP-01.yaml
...
CP-05.yaml
```

Одна попытка соответствует одному элементу `attempts` внутри файла.

Каждая попытка имеет уникальный `assessment_id` и последовательный `attempt_number`. Повторная проверка не удаляет предыдущую попытку.

Минимально сохраняются: идентификация контроля, дата/время, статус, результат, обязательные компоненты, источники проверки, результаты компонентов, недостатки, коррекция, связь с предыдущей попыткой и решение о продвижении.

## 12. Переход состояния

Значимый переход обрабатывается логически как единая последовательность:

```text
результат учебного действия/контроля
            ↓
Learning Event
            ↓
Assessment Record (если применимо)
            ↓
Learning State
            ↓
следующее разрешённое действие
```

Нельзя сообщать, что переход полностью сохранён, если необходимая запись не выполнена и не проверена.

## 13. Согласованность

Для каждой завершённой контрольной попытки:

```text
Assessment Record.assessment_id
        ↕
Learning Event.assessment_id
        ↓
Learning State.last_assessment_id
```

Для значимых событий:

```text
Learning Event.event_id
        ↓
Learning State.last_event_id
```

Если ссылки или результаты противоречат друг другу, продвижение блокируется до восстановления согласованности.

## 14. Learning State

State хранит только оперативный снимок:

- текущий раздел/урок/Unit;
- текущий контроль;
- фазу и статус;
- завершённые Unit/LCP/CP;
- активную коррекцию;
- блокирующие условия;
- следующий разрешённый шаг;
- ссылки на последние Event и Assessment.

State не является самостоятельной историей.

## 15. Правила записи в GitHub

Для существующего файла:

`READ → SHA → MODIFY → WRITE → READ BACK → VERIFY`.

Для нового файла сначала проверить отсутствие пути.

При конфликте SHA сначала перечитать актуальную версию. Нельзя вслепую перезаписывать более новую версию.

Один файл не должен изменяться параллельными операциями.

## 16. Межчатовая передача

```text
LEARNING
   │ WRITE
   ▼
GitHub / 04_Progress/
   ▲
   │ READ
   │
ORCHESTRATOR
```

Project Sources не являются оперативной базой Progress.

## 17. Правила перехода

```text
UNIT
  ├── PASSED → NEXT_UNIT
  ├── PASSED (последний Unit урока) → LCP
  └── недостаточно → REMEDIATION / RECHECK

LCP
  ├── PASSED → NEXT_LESSON
  └── FAILED → REMEDIATION / RECHECK

CP
  ├── PASSED → NEXT_SECTION
  └── FAILED → REMEDIATION / RECHECK
```

Обязательный этап нельзя пропустить.

## 18. Отчётность

Краткий отчёт строится из Progress и должен включать:

- Section / Lesson / Unit;
- прогресс Unit;
- прогресс LCP;
- прогресс CP;
- последний результат контроля;
- активную коррекцию или блокировку;
- следующее разрешённое действие.

## 19. Восстановление

Если State отсутствует или повреждён:

1. прочитать Events;
2. прочитать Assessment Records;
3. сопоставить их с каноническим маршрутом;
4. восстановить наиболее безопасное состояние;
5. при неоднозначности остановить продвижение.

Нельзя восстанавливать Progress только по памяти модели или истории чата.

## 20. Pre-launch

До официального запуска тестовые события и тестовые файлы не являются фактическим Progress.

## 21. Критерий корректного прохождения

Учебный этап считается корректно закрытым только если одновременно:

1. учебная работа выполнена;
2. обязательные компоненты получили допустимые доказательства;
3. результат отражён в Events/Assessments;
4. State обновлён и проверен;
5. следующее разрешённое действие соответствует каноническому маршруту.
