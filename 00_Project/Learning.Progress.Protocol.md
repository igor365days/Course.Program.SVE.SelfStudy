# Протокол Progress — Course.Program.SVE.SelfStudy

**Документ:** Learning.Progress.Protocol
**Версия:** 1.0
**Статус:** Канонический протокол проекта
**Применяется к:** Course.Program.SVE.SelfStudy

## 1. Назначение

Этот документ формализует полный цикл фиксации фактического прохождения курса: от начала Unit до перехода к следующему Unit, LCP или CP.

Progress — это внешнее постоянное состояние конкретного обучающегося. Он хранится в GitHub и является общим для всех рабочих чатов Project.

История чата не является постоянным Progress.

## 2. Состав Progress

```text
04_Progress/
├── Learning.State.yaml
├── Learning.Events.jsonl
└── Assessments/
    ├── LCP-01.yaml ... LCP-18.yaml
    └── CP-01.yaml ... CP-05.yaml
```

### Learning.State.yaml

Текущий оперативный снимок: Section; source Lesson; Unit; текущая контрольная точка; статус текущего объекта; завершённые Unit/LCP/CP, необходимые для маршрута; открытая коррекция; нерешённые недостатки; следующий разрешённый шаг; блокирующие условия.

### Learning.Events.jsonl

Хронологический журнал значимых событий. Новые события добавляются, исторические записи не переписываются.

### Assessments/

Фактические результаты контрольных попыток. Assessment Record не заменяет Learning Event и Learning State.

## 3. Иерархия данных

```text
Канонический курс
      │
      │ определяет маршрут и требования
      ▼
Фактическое событие / результат контроля
      │
      ▼
Learning Event + Assessment Record
      │
      ▼
Learning State
      │
      ▼
следующее разрешённое действие
```

Канонический курс определяет, что должно происходить. Learning Events и Assessment Records фиксируют, что фактически произошло. Learning State показывает, где обучающийся находится сейчас.

## 4. Роли чатов

### ORCHESTRATOR

Orchestrator читает актуальный Progress, проверяет маршрут и prerequisites, определяет следующее разрешённое действие, координирует Learning Session, контролирует переходы, записывает или координирует запись Progress и формирует краткие отчёты.

### LEARNING

Learning Session проводит обучение, выполняет практику, проводит предусмотренные проверки, получает доказательства и фиксирует значимые результаты согласно протоколу.

Обе роли используют один GitHub Progress.

## 5. Правило начала любой сессии

Перед продолжением работы:

1. Определить роль чата.
2. Получить актуальный Progress из GitHub, если он инициализирован.
3. Получить соответствующее каноническое определение курса.
4. Проверить текущую позицию и prerequisites.
5. Определить следующее разрешённое действие.
6. Только после этого продолжать обучение или управление маршрутом.

Если состояние отсутствует, противоречиво или не позволяет безопасно определить маршрут, продвижение блокируется до восстановления состояния или получения необходимого уточнения.

## 6. Жизненный цикл Unit

### START_UNIT

Условия: Unit является следующим разрешённым элементом; предыдущий обязательный элемент завершён; отсутствует блокирующее состояние.

Действия: прочитать каноническое определение Unit; установить текущий Unit; установить `IN_PROGRESS`; записать `UNIT_STARTED`; обновить Learning State.

### CONTINUE_UNIT

Проводится каноническая учебная работа: `Введение → Разбор → Управляемая практика → Самостоятельное/коммуникативное применение`. Не каждое сообщение чата является Learning Event.

### VERIFY_UNIT

1. Определить обязательные компоненты контроля Unit.
2. Для каждого компонента определить способ проверки согласно центральной политике.
3. Выполнить AI-проверку там, где она возможна.
4. Запросить `USER_CONFIRMED`, где это предусмотрено.
5. Зафиксировать результат каждого обязательного компонента.
6. Определить общий результат Unit.

### UNIT PASSED

Если все обязательные компоненты имеют приемлемые результаты: создать соответствующий Assessment Record, если модель Unit предусматривает отдельную запись; записать `UNIT_VERIFIED`; обновить Learning State; определить следующий элемент маршрута.

Следующим элементом является следующий Unit того же урока или LCP, если завершён последний Unit урока.

### UNIT NOT PASSED

Если обязательный компонент не выполнен или имеет `NOT_VERIFIED`: не открывать следующий обязательный элемент; зафиксировать недостаток; при необходимости записать `REVIEW_REQUIRED`; организовать целевую коррекцию; после коррекции провести повторную проверку.

## 7. Жизненный цикл LCP

LCP доступна только после завершения всех Unit соответствующего урока.

### START_LCP

Проверить prerequisites; прочитать каноническое определение LCP; записать `LCP_STARTED`; установить текущую контрольную точку; обновить Learning State.

### COMPLETE_LCP

Выполнить обязательные компоненты; проверить каждый компонент; создать Assessment Record попытки; определить `PASSED` или `FAILED`; записать `LCP_COMPLETED` при завершении контрольного процесса; обновить Learning State.

При успешном LCP открыть следующий урок. При неуспешном результате: `FAILED → REMEDIATION → RECHECK → решение о продвижении`. Предыдущая попытка сохраняется.

## 8. Жизненный цикл CP

CP доступна только после прохождения всех LCP, относящихся к разделу.

### START_CP

Проверить prerequisites раздела; прочитать каноническое определение CP; записать `CP_STARTED`; установить текущую контрольную точку; обновить Learning State.

### COMPLETE_CP

Выполнить обязательные компоненты; проверить каждый компонент; создать Assessment Record; определить результат; записать `CP_COMPLETED` при завершении контрольного процесса; обновить Learning State.

При успешном CP открыть следующий раздел. При неуспешном результате применить целевую коррекцию и повторную проверку.

## 9. Проверка компонентов

Для каждого обязательного компонента отдельно фиксируются выполнение, источник проверки и результат оценивания.

Источник проверки принимает значения:

```text
AI_VERIFIED
USER_CONFIRMED
NOT_VERIFIED
```

`USER_CONFIRMED` означает подтверждение обучающимся выполнения требуемого действия. Оно не является AI-проверкой.

`NOT_VERIFIED` блокирует завершение обязательного компонента.

Контроль может успешно завершиться с сочетанием `AI_VERIFIED` и `USER_CONFIRMED`, если это разрешено политикой и самой контрольной точкой.

## 10. Learning Events

Событием считается только значимое изменение или действие, влияющее на Progress.

Минимальный набор:

```text
UNIT_STARTED
UNIT_VERIFIED
REVIEW_REQUIRED
USER_CONFIRMATION_REQUESTED
USER_CONFIRMED
LCP_STARTED
LCP_COMPLETED
REMEDIATION_STARTED
REMEDIATION_COMPLETED
RECHECK_REQUIRED
CP_STARTED
CP_COMPLETED
```

Обычный вопрос, объяснение или упражнение не становятся событием автоматически.

## 11. Assessment Records

Каждая контрольная попытка должна позволять восстановить идентификатор записи; тип контроля `UNIT`, `LCP` или `CP`; объект контроля; дату/время; компоненты; выполнение каждого компонента; источник проверки; результат; недостатки; коррекцию; связь с предыдущей попыткой, если это повторная проверка; решение о продвижении.

Новая попытка не удаляет старую.

## 12. Переход состояния

Значимый переход выполняется логически как единая операция:

```text
Результат контроля
      ↓
Learning Event
      ↓
Learning State
      ↓
следующий разрешённый шаг
```

Нельзя сообщать, что переход полностью сохранён, если необходимая запись не выполнена и не проверена.

Если одна из записей завершилась ошибкой, сначала проверить фактическое состояние GitHub, затем восстановить согласованность.

## 13. Протокол записи в GitHub

Для существующего файла: `READ → получить текущий SHA → MODIFY → WRITE с текущим SHA → READ BACK → VERIFY`.

Для нового файла сначала убедиться, что путь отсутствует.

При конфликте SHA не перезаписывать файл вслепую. Сначала перечитать актуальную версию.

## 14. Межчатовая передача состояния

Постоянное состояние между чатами передаётся через GitHub.

```text
LEARNING
   │
   │ WRITE
   ▼
GitHub / 04_Progress/
   ▲
   │ READ
   │
ORCHESTRATOR
```

Project Sources не являются оперативной базой Progress.

Новый Learning Chat может продолжить курс, прочитав актуальный Progress, даже если предыдущий чат больше не используется.

## 15. Правила перехода

```text
UNIT
  ├── PASSED → NEXT_UNIT
  ├── PASSED (последний Unit урока) → LCP
  └── недостаточно → REMEDIATION / RECHECK

LCP
  ├── PASSED → NEXT_LESSON
  └── FAILED → REMEDIATION / RECHECK

CP
  ├── PASSED → NEXT_SECTION
  └── FAILED → REMEDIATION / RECHECK
```

Нельзя переходить через обязательный элемент.

## 16. Формирование краткого отчёта

Отчёт строится из Progress, а не из полного текста чата.

Минимум: Section / Lesson / Unit; Unit progress; LCP progress; CP progress; последний результат контроля; открытая коррекция или блокировка; следующее разрешённое действие.

## 17. Восстановление

При отсутствии или повреждении State: прочитать Events; прочитать Assessment Records; сопоставить их с каноническим маршрутом; восстановить наиболее безопасное состояние; если состояние неоднозначно — остановить продвижение и запросить уточнение.

Нельзя восстанавливать Progress по памяти модели или только по истории чата.

## 18. Pre-launch

До официального запуска курса тестовые события и тестовые файлы не являются фактическим Progress. Тестовые записи должны быть явно отделены от реального Progress и удалены после завершения соответствующего эксперимента, если они больше не нужны для документации теста.

## 19. Критерий корректного прохождения

Система считается корректно обработавшей учебный этап только если одновременно выполнены четыре условия:

1. учебная работа выполнена;
2. обязательные компоненты контроля получили допустимые доказательства;
3. результат отражён в Progress;
4. следующее разрешённое действие соответствует каноническому маршруту.

Если хотя бы одно условие не выполнено, этап не должен считаться полностью закрытым.
