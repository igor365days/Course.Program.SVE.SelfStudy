# Project Specification — Course.Program.SVE.SelfStudy

## 1. Назначение

Создать самостоятельный долгосрочный курс шведского языка на основе книги Е. Л. Жильцова **«Шведский язык. Самоучитель» (2-е изд., 2014)** и накопленного методического опыта проекта `Course.Program.SVE`.

Курс должен организовывать последовательное обучение, практику и контроль фактического освоения материала.

## 2. Главная цель

Организовать действия учащегося для внимательного, последовательного и полного обучения с контролем процесса и результатов, чтобы получить максимально возможный результат обучения.

Скорость прохождения не является главной целью. Приоритет имеют качество, полнота и устойчивость освоения.

## 3. Два слоя системы

### Канонический курс — GitHub

GitHub хранит программу, структуру, последовательность, Unit, разделы, LCP, CP, учебные планы, методику, ресурсы и версии курса.

### Практическое прохождение — ChatGPT Project + GitHub Progress

ChatGPT Project организует фактическое прохождение конкретным учащимся. GitHub дополнительно используется как внешнее структурированное хранилище фактического состояния, событий и результатов контроля.

`GitHub / Canonical = что и в какой последовательности изучать и контролировать.`

`ChatGPT Project = как конкретный учащийся фактически проходит курс.`

`GitHub / Progress = что фактически произошло, результаты контроля и текущее состояние.`

## 4. Каноническая архитектура

Курс содержит:

- 18 исходных уроков книги;
- 56 Unit;
- 18 LCP — контрольных точек по каждому уроку книги;
- 5 разделов;
- 5 CP — контрольных точек по разделам.

Каждая Unit относится ровно к одному уроку книги и одному разделу.

Маршрут:

`Unit → Unit → ... → LCP → следующий урок → ... → LCP → CP → следующий раздел`.

## 5. Иерархия контроля

Контроль имеет три уровня:

### Level 1 — Unit verification

Проверяет освоение конкретной Unit.

### Level 2 — LCP

Проводится после всех Unit одного урока книги. Проверяет интегрированное и самостоятельное использование существенного материала всего урока.

### Level 3 — CP

Проводится после последнего урока раздела. Проверяет интегрированное освоение материала всего раздела и является границей перехода к следующему разделу.

## 6. Ограничения проверки и пользовательское подтверждение

Система не должна создавать ложного впечатления, что AI способен объективно проверить каждый аспект изучения языка. В частности, некоторые задания на произношение, самостоятельную работу вне Project, работу с внешним аудио и другие действия могут быть недоступны для надёжной AI-проверки.

Поэтому контрольные объекты должны явно разделять источники подтверждения:

- `AI_VERIFIED` — результат проверен AI доступными средствами;
- `USER_CONFIRMED` — пользователь подтверждает выполнение специально определённого задания, которое система не может надёжно проверить;
- `NOT_VERIFIED` — необходимое подтверждение отсутствует.

Пользовательская отметка является допустимой частью контрольного протокола там, где это предусмотрено каноническим заданием. Она фиксирует выполнение действия со слов пользователя и не должна называться AI-проверкой.

Контрольная точка не может считаться полностью выполненной, если обязательный компонент имеет статус `NOT_VERIFIED`.

## 7. Методическая модель

Базовый цикл Unit:

`Введение → Разбор → Управляемая практика → Самостоятельное/коммуникативное применение → Unit verification`.

После последней Unit урока проводится LCP. После последнего урока раздела проводится CP.

## 8. Последовательность

1. Unit внутри урока проходят последовательно.
2. Unit нельзя пропускать ради удобства.
3. LCP является обязательной контрольной точкой урока.
4. После успешного LCP открывается следующий урок.
5. CP является обязательной контрольной точкой раздела.
6. Только успешный CP открывает следующий раздел.
7. При недостаточном результате организуются целевое повторение и повторная проверка.
8. Для каждого обязательного контрольного компонента должно существовать допустимое подтверждение: AI_VERIFIED или предусмотренное заданием USER_CONFIRMED.
9. Успешно завершённый LCP или CP сохраняет исторический статус `PASSED`. Последующая `REASSESSMENT` не отменяет его автоматически.

## 9. Архитектура учебных чатов

Unit является учебным объектом, но не обязательно отдельным чатом.

Основная модель Project — один непрерывный Learning Session, в котором последовательно проходят несколько Unit и при необходимости LCP. Новый чат может использоваться при операционной необходимости.

Отдельный чат для каждой Unit не является требованием.

`COURSE ORCHESTRATOR` — отдельная управляющая сессия и не заменяет Learning Session.

## 10. Learning Progress

Фактическое состояние учащегося не является частью канонического курса.

Для фактического прохождения используется отдельный слой `04_Progress/` в GitHub.

Каноническая структура:

```text
04_Progress/
├── Learning.State.yaml
├── Learning.Events.jsonl
└── Assessments/
    ├── LCP-01.yaml ... LCP-18.yaml
    └── CP-01.yaml ... CP-05.yaml
```

### Learning.State.yaml

Компактный текущий снимок состояния учащегося: текущий раздел, урок, Unit, контрольная точка, завершённые этапы, открытая коррекция и следующий разрешённый шаг.

State является оперативным представлением и может быть восстановлен из исторических данных.

### Learning.Events.jsonl

Хронологический append-oriented журнал значимых учебных событий. Он не является стенограммой чата.

### Assessments/

Отдельные компактные записи фактических результатов LCP и CP. Каждая запись сохраняет результат, компоненты контроля, источник подтверждения, дефициты, коррекцию, повторную проверку и решение о переходе.

## 11. Принцип источника истины

Исторические Learning Events и Assessment Records являются основанием для восстановления состояния. `Learning.State.yaml` является текущим оперативным снимком, а не независимой историей.

Исторические записи не должны молча переписываться или уничтожаться из-за нового результата. Повторная проверка создаёт новый результат, сохраняя предыдущий.

`REASSESSMENT` применяется только к уже успешно закрытому LCP/CP. Отрицательный результат такой повторной оценки не отменяет исторический `PASSED`, если отдельное каноническое правило явно не устанавливает иное.

## 12. Отчётность

Структура Progress должна позволять ChatGPT формировать краткие отчёты без хранения заранее подготовленных отчётов.

Минимально должны быть доступны:

- текущее положение в курсе;
- общий прогресс по Unit, LCP и CP;
- последние результаты контроля;
- текущие дефициты и необходимость коррекции;
- следующий разрешённый шаг;
- краткий статус каждого завершённого раздела.

Подробные стенограммы учебных чатов в Progress не дублируются.

## 13. Форматы

- Markdown — спецификации и правила;
- YAML — текущее состояние и структурированные результаты контроля;
- JSONL — исторический поток событий.

Выбор подтверждён практическими тестами работы ChatGPT Go с GitHub.

## 14. Реализация Progress

ChatGPT Go через подключённый GitHub способен читать, создавать и изменять UTF-8 текстовые файлы Progress с фиксацией изменений в GitHub.

Перед изменением существующего файла необходимо получить его актуальную версию и текущий blob SHA. После изменения результат должен быть повторно прочитан и проверен.

Физический механизм конкретных действий Orchestrator с GitHub формализован в `Learning.Progress.Protocol.md` и `Course.Orchestrator.Specification.md`.

## 15. Pre-launch

Проект пока не используется для реального обучения. Архитектуру, структуру файлов, разделы, Unit, контрольные точки и инструкции можно свободно перерабатывать до начала реального прохождения.

## 16. Канонический протокол Progress

Полный жизненный цикл фиксации прохождения формализован в:

`00_Project/Learning.Progress.Protocol.md`

Дополнительная семантика повторной оценки уже пройденных LCP/CP формализована в:

`00_Project/Assessment.Reassessment.Policy.md`

Протокол определяет:

- начало и завершение Unit;
- проверку обязательных компонентов;
- переход Unit → LCP → следующий урок;
- переход LCP → CP → следующий раздел;
- целевую коррекцию и повторную проверку;
- правила `AI_VERIFIED`, `USER_CONFIRMED`, `NOT_VERIFIED`;
- структуру значимых Learning Events;
- Assessment Records;
- обновление Learning State;
- межчатовую передачу состояния через GitHub;
- восстановление Progress;
- краткую отчётность;
- критерий корректного закрытия учебного этапа;
- сохранение исторического `PASSED` при `REASSESSMENT`.

Этот документ является каноническим протоколом практического Progress и дополняет спецификацию Orchestrator, стандарты файлов, State Machine и политику проверки.
